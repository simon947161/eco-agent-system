## 0. 修订判断与 Founder 意图

上一阶段把 W3C 可验证凭证、SCITT 视为后期可选签名增强，这一判断**不充分**。Founder 要求从一开始研究区块链式知识组织：每份原始资料、每项条款、每一个节点、每条关系、每次审查、每次推断和纠错，都能够被寻址、验证、追溯、重放，并且允许从不同入口探索隐藏的跨领域关联，形成逐步增长的知识与可审计认知。

**新的战略目标**：不止把 CSP/LSPS/LEP/DCP/DP/OP 画成“知道谁连谁”的图，而是逐步建立一种可以回答 **“这个判断从哪些字节/文档片段、哪些证据和哪些推理路径来？这些证据何时改变？是否存在另一条未被看见但值得验证的路径？反证是什么？”** 的可信知识系统。

采用 **blockchain-informed** 的组织原则，并不预设必须发行代币、采用公开链、部署共识网络、把每个字节做成独立区块，或把具有官方性质的文件作为自有“签发凭证”。实现“每个字节可核验”的可行途径通常是：对获准保存的原始文件字节做完整性哈希；以固定规则分块并构建 Merkle 树/有向无环内容图；用位置映射关联文本提取、条款语义对象；对每次关系断言和审核事件链接前版哈希。**研究必须先比较和验证这套定义在不同文件格式上的边界**。

**身份、真伪、可信度严格分开**：字节哈希只能证明与某份受检快照一致；来源 URL 及抓取时间不等于发布者数字签名；研究者的签名只能归属研究者的声明；透明收据只能证明被收录，不保证声明内容正确；官方法规效力、科学结论、项目绩效与因果判断要另经专业证据核定。

## 1. 四种互联而不混同的结构

**1. 内容与来源图（Content/Provenance DAG）**
- 原始官方来源 → 合法获取的字节快照/元数据 → 分块与内容哈希 → 可定位原始字节范围/页码 → 抽取的条款 → 语义节点。
- 同文件不同版本有各自根哈希及合法保留的源链接；新版本必须明确替代/补充关系，不可覆盖旧哈希。
- 不允许脱离原件把模型归纳出的摘要当作原始资料；抽取过程需记录工具、算法版本、字节坐标/页锚、置信度与失败状态。

**2. 语义关系知识图（Semantic Assertion Graph）**
- 语义节点不是裸文字，必须关联来源和时点；边是一级对象，具备 `edge_id, source, predicate, target, asserted_by, reviewed_by?, evidence_refs[], region_scope, valid_from/to, source_version, epistemic_status, counterevidence_refs[], algorithm_version?`。
- `EXPLICIT_OFFICIAL`、`RESEARCH_INFERRED`、`HYPOTHESIS_ONLY`、`SYNTHETIC`、`CONTRADICTED`、`SUPERSEDED` 是**不同声明状态**；不可仅因两跳成立就把第三跳升成官方关联。
- CSP→DP→OP 的官方执行层级，与 LSPS↔LEP/DCP/SEPP 的空间规划和法定效力不同；同一 LEP/DCP 对不同地区、生效日期可能适用性不同。
- 一个项目同时关联多个战略目标、多个法规/政策来源时保持多对多，不能把“有联系”误认为“有法律从属”。

**3. 时间与治理事件链（Append-only Review/Event Log）**
- 对 `SOURCE_OBSERVED, NODE_DERIVED, EDGE_PROPOSED, EDGE_REVIEWED, DISAGREEMENT_RECORDED, EDGE_RETRACTED, REVISION_SUPERSEDED, PROOF_VERIFIED, ACCESS_REVOKED` 等事件定义 actor、事件时点/来源事实时点、前事件哈希/承诺根、对象、理由及相关证据引用。
- 不擦除错误：以后发更正/撤回/废止事件，当前视图计算出正确有效状态，同时可重演历史视图；审计记录不得无限保留受法律保护的私密原文。
- 区分本地防误改哈希日志与真正防恶意历史改写的外部独立见证/签名/透明服务；无第三方验证时**不能宣称不可篡改**。

**4. 智能发现与反证路径（Inference/Discovery Graph）**
- **暗线**是跨战略、法规、环境指标、行动、风险、证据等的多跳潜在路径；由路径查询、跨文件术语匹配、实体对齐、时空重合、规则、语义检索等产生，但**仅是候选解释**。
- 每条暗线必须给出逐跳证据、搜索规则/模型版本、反面证据、替代解释、时空条件、审查状态与“不足以证明”的原因；不得形成已确定的制度责任/法定义务/项目绩效。
- 需要支持“为什么找到这条暗线”“为什么这条没有获得确认”“如果 2026 版本替代旧版，该路径哪些部分失效”三类询问。

## 2. 每个字节可审计——技术可验证定义

研究不采用“每一个字节单独入链”的字面实现，而采用如下可验证能力目标，明确可靠性与限制：

1. `raw_hash`：对可合法保留的原始文件**确切字节**按记录算法（例如 SHA-256）计算摘要；比较任意一字节改动能否检测变化。文件再发布、压缩或换行改变会改变 raw_hash，不自动等于语义被篡改。
2. `content_blocks`：对获准保存的原始内容定义明确的分块方法（固定尺寸 vs 内容定义分块）及边界、偏移、大小、媒体类型；比较 Merkle 根/包含证明是否值得在 V1 实施。不必永久储存逐字节小块。
3. `semantic_hash`：对于结构化节点、边与审查声明，规定稳定的**规范化序列化**、字段排序、UTF-8/Unicode 处理、空值、浮点数和模式版本，防止语义等价对象无意生成不同摘要。**不要把 semantic_hash 当作 raw_hash**。
4. `content_address`：选取带算法标识与编码版本的内容标识/CID 设计；若采用 IPLD 或类似模型，需记录许可及编码约束，不强求任何 IPFS 网络或外部托管。
5. `evidence_anchor`：条款具有文档版本、页/条号、原始字节范围（有意义时）/文本定位锚；PDF/图像的 OCR 或重排不可确保像源文本那样的逐字节段对应，必须标 `EXTRACTION_UNCERTAIN`。
6. `reproduce`：由样本原件、规范和版本日志能重现哈希、关系图快照及研究推断路径；不同机器及工具版本的漂移必须暴露。
7. `correction/privacy`：版权许可、个人信息、保密责任与删除要求凌驾于“永远存储原文”的假设；必要时保留允许的校验元信息、撤销访问并记录合法更正，不把敏感内容（包括可被字典猜测的哈希）上传公开链。

## 3. 标准与候选技术：必须实际查证，而不直接预选

以 2026-10-29 官方文件为研究线索：

- W3C 可验证凭证数据模型 v2.0（2025-05-15 推荐标准）及 JOSE/COSE 安全规范（2026-10-13 推荐标准）：研究签发者身份、主体、验证者、凭证状态与选择性披露；区分 Council 正式签发与 Atlas 研究者自述，不能冒名。
  - https://www.w3.org/TR/vc-data-model-2.0/
  - https://www.w3.org/TR/vc-jose-cose/
- IETF RFC 9943 SCITT（2026-06，Proposed Standard）及 RFC 9942 COSE Receipts（2026-06，Proposed Standard）：研究可验证声明、透明登记、可独立验证收据、Merke 包含/一致性证明，以及其**不验证声明真值**的限制。
  - https://www.rfc-editor.org/info/rfc9943/
  - https://www.rfc-editor.org/info/rfc9942/
- 内容寻址与 Merkle DAG：研究 Git 对象哈希/提交历史、IPLD/CID、Merkle 结构、构建成本、块边界与本地存储方式；与可用的 ClimateOS Evidence Passport/Run Receipt/Source Revision 逐字段对照。
- 如出现长期多主体共同签发/跨机构防抵赖要求，再比较私有透明日志、许可链、公有链锚定的实际必要性和成本。未证明多方不互信且需共识之前，不启动共识服务、代币或昂贵云存储。

每项技术必须给出：**解决的具体问题、威胁模型、可证明什么、不能证明什么、是否存在更简单替代、维护成本、失败和撤销方式**。不准因为行业热词而将某产品定为不可替代依赖。

## 4. 横向有机树 UI：知识树生长、暗线发光、证据可查

保留 V1.1 R0 的**横向不等长但布局稳定的有机树**，面向单大屏、超宽屏及双显示器。默认只显示轻量标签、局部 1–2 跳；点击或键盘聚焦时在证据抽屉展开，右栏可显示多个路径证据及反证比较。

新增 UI 模式：

- **官方路径**：有出处的 CSP/DP/OP 执行路径，及独立的 LSPS/LEP/DCP 适用网络；不可通过图形位置伪造层级。
- **可信链路**：点击节点/分支查看原始来源、字节快照哈希、引文定位、版本替代链、审核记录、是否存在有效数字签名/SCITT 收据；未签名显示 `NO_CRYPTOGRAPHIC_PROOF` 而不是验证通过。
- **暗线探索**：从任意两节点生成/检索最多若干条多跳**候选**连接；候选以不同线型或荧光轮廓表明“不确定”，点击可看到路径上的各个论据和反证；没有足够证据时显示断点，不能自动生成权威结论。
- **时间回放**：切换 as-of 日期，追看各文件的旧版关系何时被提出、复核、撤回；失效关系淡化，不从历史抹除；按需展开证据。
- **有机成长**：灰底为固定几何路径，彩色填充可选 `REVIEW_COVERAGE`、`TIME_ELAPSED`、`ADMITTED_PUBLIC_KPI`，独立标明分母/期间/方向/来源；证据数量增加不能当战略绩效，实际结果未知不能当 0%，负向绩效另有数值和趋势标注。
- **多路径审计**：对同一结论可选择路径 A/B 并排对比来源不同、版本/地域冲突、节点缺失；点击“一键查看哪一跳未核实”，不能把“发现暗线”呈现为正式决策建议。
- **双显示器**：研究两窗口协作状态共享，不假设单个网页自动横跨两屏；先保证普通单屏清晰可用。

设计时确保颜色不是唯一判断手段、键盘/触屏可操作、长标签不会遮挡，折叠和缩放不会改变同一版本图形位置的确定性。

## 6. R0-K 必须回答的六个架构决策

1. **内容寻址粒度**：文件、页/段落、字节块各自能证明什么，哪一个才值得维护？“每字节受保护”如何以可重复校验低成本实现？
2. **三类时间**：来源发布、生效/废止、研究发现/审核时间怎样分别组织？如何处理链接消失及官方改版？
3. **暗线发现的证据预算**：哪些路径是直接引用、哪些是研究关联、哪些由 AI 建议？多跳推理如何输出反证和“未知”？
4. **真实性与权威**：本地哈希、研究者签名、官方电子签名、外部收据、法律适用、科学证据分级怎样在 UI 清楚区分？
5. **法律与隐私**：公共文件许可、可删除性、保密信息、哈希泄露、版权和 Council 身份冲突怎样治理？
6. **演化与互操作**：当前 ClimateOS/WCOS 模型可以复用什么、哪些字段需要升级，如何不引入大型数据库或商业平台？

## 8. R0-K 核验 / 反例测试

研究阶段先设计并说明后续如何重复测试：

1. 官方原始文件发生**单字节变化**，raw_hash 变化；新版本保留旧根和审查记录。
2. 同一语义节点不同字段顺序经规范化得稳定 semantic_hash；原文内容不同/来源不同不能借摘要合并为一个“官方对象”。
3. 一条关系由两份材料推断，但官方文件没有明说；UI 不能把 `RESEARCH_INFERRED` 提升成 `EXPLICIT_OFFICIAL`。
4. 发现两条互相矛盾的暗线；两种路径及反证都可展开，不能强行给单一答案。
5. 旧版 LEP/DCP 或外区文件被拿来支持当前 Berridale 结论；适用性断言失败，标 `VERSION_OR_SCOPE_CONFLICT`。
6. 研究者本地签名/透明日志已核验，但文件并无 Council 正式数字签名；不得显示“官方加密认证”。
7. 用户撤回有版权/隐私风险的内容；系统按访问与保留政策清理，保留合法的更正/撤销审计记录，不因“不可变”将敏感原文永久公开。
