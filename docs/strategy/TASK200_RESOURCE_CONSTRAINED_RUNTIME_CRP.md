## 1. Context

This CRP records a follow-up discussion after the Task200 AI sovereignty and resilience strategy seed.

The discussion was triggered by a reported example of a hand-cranked AI device, described informally as **CrankGPT**: a small offline AI hardware concept that could run a roughly 1B-parameter model without normal grid power or internet access.

Whether this exact device becomes important is not the key point.

The strategic value is that it clearly echoes the Task200 question:

> If the network is gone, if power is limited, if cloud APIs are unavailable, can AI-assisted governance still continue in some reduced but living form?

This gives ClimateOS a new Task200 design direction:

> **Resource-Constrained Runtime** — the ability of ClimateOS to preserve useful reasoning, observation, validation, and governance functions under limited energy, limited compute, limited data, and limited connectivity.

---

## 2. Core Insight

The important insight is not the hand crank itself.

The important insight is:

> AI does not have to equal cloud AI.

AI can exist at several scales:

- national AI infrastructure;
- regional AI runtime;
- community AI runtime;
- household / edge AI runtime;
- personal survival AI runtime;
- human-only paper-and-memory runtime.

For ClimateOS, this means that the system should not only be designed for ideal online conditions. It should also define what capability remains when the world becomes constrained.

---

## 3. Task200 Design Principle

The following principle should be considered for Task200:

> **The value of a governance system is not measured only by how well it performs under ideal conditions. It is measured by how much useful capability remains when conditions become constrained.**

In Chinese:

> 一个治理系统的价值，不只取决于它在理想条件下有多强，而取决于在资源受限、网络中断、极端事件发生时，还能保留多少有用能力。

This principle should become part of the future ClimateOS resilience architecture.

---

## 4. Resource-Constrained Runtime Levels

Task200 should consider a multi-level runtime structure.

### Level 1 — Cloud Runtime

Normal operating mode.

- OpenAI / Claude / Gemini / other cloud models;
- GitHub / cloud storage;
- online research;
- high-compute reasoning;
- normal API access.

### Level 2 — Hybrid Runtime

Cloud plus local fallback.

- cloud models for advanced reasoning;
- local models for continuity;
- local document archive;
- local Obsidian / GitHub mirror;
- degraded but continuous operation.

### Level 3 — Local Runtime

No cloud model dependency.

- local LLMs;
- local knowledge base;
- local scripts;
- local evidence records;
- local CRP / CARP archive;
- limited but independent reasoning.

### Level 4 — Survival Runtime

Extreme-resource mode.

- laptop, mini PC, Raspberry Pi, or similar edge device;
- battery / solar / hand-crank / small generator power;
- small local model;
- compressed knowledge pack;
- disaster response notes;
- essential governance templates.

This is the conceptual area suggested by the hand-cranked AI example.

### Level 5 — Human Runtime

If computation is unavailable.

- printed documents;
- maps;
- observation diaries;
- CRP summaries;
- decision templates;
- local knowledge;
- human memory and judgment.

This is the final fallback layer of ClimateOS as a civilization seed system.

---

## 5. Relationship to ClimateOS

ClimateOS is not only a software system.

It is intended to become a runtime for evidence-based environmental, climate, energy, water, land, and regional governance reasoning.

Because its operating domain includes extreme climate events, it must assume that disruption is not an exception but a design condition.

Relevant disruption scenarios include:

- bushfire;
- flood;
- drought;
- heatwave;
- grid failure;
- communication failure;
- cloud platform failure;
- API access restrictions;
- geopolitical interruption;
- war-like infrastructure damage;
- local isolation after disaster.

Task200 should therefore ask not only how ClimateOS becomes more powerful, but also how it remains minimally alive under pressure.

## 6. CRP Record

### Core Knowledge Points

- Hand-cranked or low-power AI hardware is not only a novelty; it points to the broader question of AI continuity under resource constraints.
- AI should not be equated with cloud access.
- ClimateOS should define multiple runtime levels from cloud mode to human-only mode.
- Extreme climate disruption can create similar operating constraints to war or infrastructure collapse.
- Offline and low-compute modes should be treated as part of ClimateOS survival architecture.

### Idea Points

- Introduce **Resource-Constrained Runtime** into Task200.
- Treat Survival AI as a legitimate design layer, not a joke or gadget category.
- Define ClimateOS capability degradation levels instead of assuming all-or-nothing operation.
- Add a final Human Runtime layer based on paper, memory, maps, and decision templates.

### Wish Points

- Preserve the living seed of ClimateOS even when cloud AI, internet, or normal power is unavailable.
- Keep ClimateOS useful to local communities during extreme climate or infrastructure disruption.
- Allow future agents, Codex, Obsidian, and GitHub strategy documents to remember this concern.

### Reasoning Points

- If ClimateOS only works under perfect digital conditions, it is fragile.
- If ClimateOS can degrade gracefully, it becomes a resilience system rather than only an intelligence system.
- A small local model plus compressed knowledge may be weaker than cloud AI, but it can still preserve continuity.
- If even computation is unavailable, human-readable records and templates become the final runtime.

### Key Decision

Task200 should include **Resource-Constrained Runtime / Survival Runtime / Human Runtime** as part of the AI sovereignty and resilience strategy.

### Unresolved Questions

- What is the minimum local model size that can still support useful ClimateOS reasoning?
- What should be included in the first ClimateOS Offline Knowledge Pack?
- How should local evidence, observation diaries, and CRP records be compressed for offline use?
- What hardware level is realistic for a community resilience version of ClimateOS?
- Can solar, battery, small generator, or hand-crank concepts support emergency AI usage?
- How should ClimateOS define graceful degradation from Cloud Runtime to Human Runtime?

## 7. Reminder for Future Task200

Do not dismiss low-power or offline AI examples as toys.

They may be primitive signs of a deeper design problem:

> In the hardest conditions, what remains of intelligence?

For ClimateOS, the answer should not be zero.

The system should degrade, simplify, compress, and fall back — but it should not disappear.
