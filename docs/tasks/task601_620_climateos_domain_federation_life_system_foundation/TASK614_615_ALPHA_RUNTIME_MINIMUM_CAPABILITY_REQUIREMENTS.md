# Task614-615 Alpha Runtime Minimum Capability Requirements

## Purpose

Define conceptual minimum requirements for a future Alpha Runtime without
starting Alpha Runtime implementation.

## Status

This is a non-operational requirements note. It is not runtime architecture,
application code, backend design, API design, database schema, MCP tool design,
CLI design, authentication design, deployment design, or implementation
authorization.

## Minimum Capability Requirements

A future Alpha Runtime should not be considered until it can conceptually
support:

- domain registry with explicit scope and ownership;
- evidence record intake with source and method context;
- cross-domain Evidence Contract draft records;
- human review state tracking;
- Founder Gate state tracking;
- uncertainty and disagreement preservation;
- prohibited-use labels;
- private-asset exclusion controls;
- manual export for review;
- auditability of human edits and status changes;
- clear stop conditions.

## Minimum Non-Capabilities

A future Alpha Runtime must not initially include:

- automated scientific conclusion generation;
- compliance, assurance, or certification claims;
- scoring;
- live external model connectors;
- live source retrieval;
- sensors;
- automation;
- autonomous agents;
- EcoChain;
- deployment;
- private EcoEngine integration.

## Validation Before Any Future Build

Before any Task621+ implementation gate, the project should validate:

- at least three domain example workflows;
- human review states;
- rejected and disputed evidence flows;
- private-asset exclusion rules;
- export and audit requirements;
- exact prohibited capabilities.

## Open Questions

- Should Alpha Runtime begin as file-based review, local prototype extension,
  or a separate bounded app?
- Which domains are required for the first Alpha Runtime slice?
- What evidence examples are safe, non-sensitive, and representative?
