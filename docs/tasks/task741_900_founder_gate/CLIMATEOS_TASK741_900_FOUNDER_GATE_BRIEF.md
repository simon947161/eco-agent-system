# ClimateOS Task741-900 Founder Gate Brief

Version: v0.1

Date: 2026-07-11

Status: Draft for Founder decision

Authorization effect: Planning only; not executable authorization

## 1. Decision Purpose

This brief defines the next bounded ClimateOS progression after the verified
Task721-740 closure. It does not start Task741, authorize implementation, or
permit any capability prohibited by the current Task740 hard stop.

The decision is whether the existing synthetic, localhost-only, persistent
Alpha Review Loop should now be tested as a usable human review instrument,
kept in documentation-only preparation, or expanded more broadly.

batch begins.

## 3. Strategic Question

The next phase should answer a human question before a technology question:

> Can a sustainability practitioner use the bounded local ClimateOS Alpha to
> inspect evidence, challenge it, preserve uncertainty, record responsibility
> and recover history without mistaking the system for an authority?

Task741-900 should gather evidence for that decision. It should not declare the
prototype production-ready or turn Alpha experimentation into an operational
environmental conclusion system.

## 4. Founder Decision Options

### Option A - Documentation And Test Design Only

Prepare protocols, templates, acceptance criteria, synthetic cases and future
implementation briefs. Do not modify runtime code, schema, API or user
interface.

This has the lowest technical risk but cannot establish whether the existing
Alpha is usable by a real human reviewer.

### Option B - Bounded Local Human Use Trial (Recommended)

Permit limited improvements to the existing localhost prototype only where
needed to run repeatable, synthetic/public-safe, Founder-controlled use trials.
Prioritize human comprehension, evidence challenge, uncertainty, auditability,
recovery, accessibility and exit criteria over new capability.

This option allows Task741-900 to produce a credible Alpha acceptance decision
without authorizing live sources, external models, automation or deployment.

### Option C - Expanded Alpha Integration

Permit mock adapter execution, broader domain flows and a larger technical
surface while remaining local. This may generate more engineering output, but
it risks outrunning human-use evidence and reopening trust boundaries too
early. It is not recommended for this gate.

## 5. Recommended Task Map

The following map applies if the Founder selects Option B. Every batch requires
its own verified preflight, closure record and hard stop. A broad Task741-900
authorization may permit continuous execution through Task900 only if it names
this map and preserves every boundary in this brief.

## 6. Authorized Technical Envelope Under Recommended Option B

If separately activated, work may modify only the existing bounded local stack:

- Python and FastAPI bound to localhost only;
- SQLite local persistence with reviewed additive migration only when an
  evidenced trial requirement makes it unavoidable;
- local HTML, CSS and JavaScript;
- synthetic/public-safe fixtures;
- foreground, manually initiated operations;
- repository-local tests, scripts and documentation.

Any schema change requires explicit justification, preflight, dry-run,
idempotency, integrity, backup, restore and rollback evidence. No schema change
is presumed by this brief.

## 7. Mandatory Boundaries

All Task741-900 work must remain:

- localhost-only;
- single-user and Founder-controlled;
- synthetic/public-safe;
- Human Review controlled;
- foreground and manually initiated;
- non-operational and non-production;
- evidence-preserving and non-destructive;
- clear that reviewer labels are declared labels, not authenticated identity;
- clear that hashes prove content integrity, not truth or authority.

## 8. Prohibited Capabilities

- access to private EcoEngine assets or `D:\eco_engine_v200`;
- external or live AI/model-provider connections;
- live environmental data or network import;
- MCP, n8n, QCloud or third-party service integration;
- authentication, identity verification or multi-user tenancy;
- autonomous agents, automated approval or automated decision-making;
- background workers, schedulers or unattended execution;
- scoring, ranking, certification, compliance or assurance conclusions;
- scientific truth claims, regulatory advice or public disclosure conclusions;
- cloud persistence, telemetry, deployment or public release;
- PR, merge, release or tag unless separately authorized;
- Task901 or any automatic next phase.

## 9. Execution And Evidence Rules

Before Task741 and before each later batch, Codex must verify repository,
branch, remote, HEAD, origin alignment, worktree ownership and the preceding
closure. A failed baseline is a blocker, not a pass.

Implementation must follow evidence rather than task-number pressure. Tests
must not be weakened to obtain a green result. Mutable databases, temporary
files, backups and local trial records must not be committed. Validated source,
tests and governance records may be committed and non-force pushed to the
official branch only when the executable authorization explicitly permits it.

Each batch closure must report:

1. starting and final SHA;
2. files changed;
3. trial or validation evidence;
4. schema and migration status;
5. integrity, backup and restore status where applicable;
6. isolated and complete test results;
7. `git diff --check`;
8. prohibited-capability review;
9. commit and non-force push status;
10. local/origin alignment and the next hard stop.

## 10. Stop Conditions

Stop immediately if work requires a prohibited capability, private asset,
unresolved ownership conflict, destructive history rewrite, force push,
unsupported scientific claim, or an expansion beyond the selected option.

Stop at every twenty-task closure if its acceptance evidence is incomplete.
Under a future continuous Task741-900 authorization, continuation is permitted
only after the current batch is green and its closure record is written.

Task900 is an absolute hard stop. Task901 requires a new Founder Gate.
