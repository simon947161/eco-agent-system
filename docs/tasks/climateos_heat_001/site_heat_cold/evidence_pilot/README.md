# 真实工业冷热证据试点｜Founder 审阅入口

问题是：生产计划和两端负荷时序改变后，什么证据足以支持增加热泵、直接回收或跨班储热？本次选取两个各自完整的证据窗口，各回答一个子问题。

| 证据 | 复算结果 | 对决定的影响 |
|---|---|---|
| Hardwick，澳大利亚，两期项目方运行摘要 | 年化源侧热量按报告热功率和年化小时数重建，从 6978.192 降到 4653.376 MWh。对称分解中，时数项占降幅约 62.5%。 | 扩容测算先复核实际班次和运行时数。同期供货、设定值和季节覆盖均有变化，不能把 62.5% 当作干旱的因果贡献。 |
| 挪威鱼加工厂，2021 年 1 月连续 240 个小时 | 按制冷系统 1 的电功率排序，最高和最低各 60 小时，电锅炉平均功率分别为 22.82 和 217.53 kW。 | 先查电锅炉何时运行，再检验是否有合适温级的热可供储存。这些记录能帮助定位测量时段；系统电功率不能直接换成可收集的热。 |

Hardwick 第二期节气分项加总比发布总量多 8 GJ/年，原值及差异均保留。两场地均缺同一产量、冷库温度、热水质量/温级与交付时间下的三方案对照。真实储热增量、年度净碳、全厂峰值影响及投资回报均为 DATA_NOT_READY。下一份数据应同步覆盖热侧温度/流量、用户实际取水、储罐温度/容量、生产班表，以及原供能和新增设备的计量。污水及甲烷沿用 #191 的分账与实测门槛；空间距离沿用原稳态适用范围，未运行 #187。

## 执行与重放
在当前目录运行以下命令，Python 3.10+，标准库即可。

```sh
python run.py
python agent/check_discovery.py
python agent/discover.py agent/example_job.json --state-dir /tmp/heat-discovery-test
python run.py --candidate-receipt agent/offline_receipt.json
```

第一条会重建并核对两份定量回执以及清洗后的逐时表。最后一条返回 REQUIRES_SOURCE_REVIEW，因为样例是虚构的候选。实际候选命中已验收的 DOI 后才复跑对应算法。陌生数据集须补许可、字段映射、计量边界和验证样例，再登记新的计算入口。相同任务与不同预算的处理、定价和组织凭据由执行说明约定。[API 运行说明](agent/API_RUNBOOK_CN.md)
